# OpenRD协作平台设计建议

**文档目标**：根据近期共建者讨论，明确平台的核心协作机制、用户分层、任务流转及激励体系，为前端设计与开发提供清晰、可执行的设计依据。

---

## 一、核心设计原则

1.  **低门槛进入，高价值参与**：注册开放，但通过流程设计自然筛选有诚意、愿贡献的共建者。
2.  **灵活协作，拒绝僵化**：不强求团队，但提供组队工具；任务分级，匹配不同能力与意愿的开发者。
3.  **以人为本，长期激励**：积分与激励不止于物质，更强调社区认同、情感连接与成长体系。

---

## 二、用户分层与准入机制

**设计目标**：解决“共建者进入条件既不能太苛刻，也不能太宽松”的问题，同时实现“不做白嫖式社区”。

**用户三档分层**：

| 用户档位      | 达成方式                                                     | 核心权限                                                     |
| ------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **1. 围观者** | 注册即默认。完成一个极简新手任务（如：给2500万病友写一句鼓励的话）。 | 浏览公开内容，了解社区。**不能**参与任何任务或协作。         |
| **2. 参与者** | 围观者完成《互助协议》客观题测试（系统自动判卷）。           | 可查看、认领**小型任务**（如修bug、写文档），参与社区讨论。  |
| **3. 职业者** | 参与者完成职业认证（选择“病友/医护/开发者”等身份）。         | 可认领**中大型任务**，创建/加入队伍，获得职级晋升资格，享受更多权益。 |

**前端关键点**：

-   实现三档状态下的**权限控制**（路由、按钮、API请求）。
-   设计《互助协议》测试的**轻量化弹窗流程**（客观题，自动判卷，即时反馈）。
-   职业认证表单需支持动态选项，便于未来扩展新角色。

---

## 三、任务协作机制

**设计目标**：解决“以团队形式接单可能会有难度”的问题，适配当前以自由开发者为主的群体。

**任务分级与认领规则**：

| 任务类型               | 定义与示例                                                   | 认领方式                           | 协作模式                                                     |
| ---------------------- | ------------------------------------------------------------ | ---------------------------------- | ------------------------------------------------------------ |
| **小型任务**（个人级） | 范围清晰，单人可完成。例：修复特定bug、写一个UI组件。        | **个人直接认领**（参与者及以上）。 | 独立完成。                                                   |
| **中型任务**（协作级） | 需2-3种角色配合。例：为某功能开发配套后端API+前端页面。      | **个人认领后，平台协助组队**。     | 认领者成为“临时队长”，平台（Khub团队）协助在项目群中拉取所需其他角色，自由协作完成。 |
| **大型任务**（项目级） | 复杂度高、周期长。例：为一个罕见病关爱组织开发数据看板系统。 | **仅限官方认证团队认领**。         | 平台Khub团队会将其拆解为多个中型/小型任务，分配给不同团队或个人。专项研究（如黑客松）单独组织。 |

**队伍机制**：

-   平台提供组队板块，**职业者**可创建队伍、招募成员。
-   队伍初期不强求，但长期活跃、配合默契的队伍可获得官方认证，优先承接大型任务及专属权益。

**前端关键点**：

-   任务卡片需明确标注**类型（小/中/大）** 与**所需角色**。
-   实现“个人认领后触发展开协作”的交互（如：认领中型任务 → 弹窗提示“需要后端？点击邀请平台协助组队”）。
-   设计队伍主页，展示成员、分工、过往任务评价。

---

## 四、角色与职级体系

**设计目标**：让共建者有明确的成长路径，并通过实绩获得认可。

**核心角色**（注册/职业认证时通过问卷推荐或自选）：前端、后端、产品、运维、测试、UI/UX。

**职级晋升**（基于贡献实绩）：

-   **依据**：完成悬赏任务数量与评分、PR/设计稿被合并次数、团队协作评价等。
-   **流程**：系统根据数据自动推荐 → 核心成员（Khub或高阶用户）复核 → 晋升。
-   **激励**：职级晋升时配套发放**实体礼品**（患者手写信、纪念拍拍卡、虚拟称号等），前端需在个人主页和勋章墙有醒目展示。

**前端关键点**：

-   设计清晰的**个人贡献档案页**，展示任务完成记录、PR合并记录、当前职级与下一级差距。
-   实现**晋升动画/通知**的展现，强化仪式感。

---

## 五、积分与激励体系（问卷前框架）

**设计目标**：提供驱动力和人文感，但**具体积分权重和兑换物品待问卷调查后细化**。

**积分获取**（基础框架）：

-   **任务完成**：根据任务大小、评价获得积分。
-   **日常打卡**：每日签到得连续积分。
-   **社区贡献**：优质回答、有效文档、帮助他人等。

**兑换方向**（待定，但概念确认）：

-   **物质**：礼品卡、实物周边。
-   **精神/特权**：患者手写信（限量）、优先接单权、内部技术分享会资格。
-   **人文特色**：**每日寄语机制**。签到后，系统随机推送一条其他用户留下的寄语，并邀请用户写下一句（可鼓励患者、感谢伙伴等）。寄语库需审核，形成正向内容循环。

**前端关键点**：

-   设计**签到+寄语联动组件**：签到成功 → 弹窗或嵌入区域展示随机寄语 → 显示输入框。
-   积分商城页面需支持灵活的兑换项展示（待后端配置）。
-   用户个人资料页显示总积分、当前等级、可兑换特权。

---

## 六、方案总结

| 模块       | 核心共识设计（v1.1）                                   | 解决的问题                                       |
| ---------- | ------------------------------------------------------ | ------------------------------------------------ |
| 用户分层   | 围观者 → 参与者(协议测试) → 职业者(身份认证)，全程自动 | 平衡门槛与诚意，过滤白嫖，无人工审核负担。       |
| 任务协作   | 任务分级（小/中/大），个人认领为主，平台协助临时组队   | 适配自由开发者，提供灵活协作路径，避免任务僵死。 |
| 角色与职级 | 问卷推荐/自选角色，基于实绩自动推荐晋升，配套实体激励  | 长期激励，明确成长路径，增强归属感。             |
| 积分与人文 | 积分获取框架 + 签到/寄语联动，具体权重待问卷确定       | 驱动日常参与，塑造温暖社区认同感。               |

---

### 建议

1.  **状态管理**：用户的三档状态（围观者/参与者/职业者）会贯穿几乎所有功能，建议在全局状态（如Redux、Pinia）中设计清晰的`userRole`字段，并基于此封装权限指令（如`v-role="'participant'"`）。

2.  **组件复用**：不同任务类型（小/中/大）的卡片展示、认领按钮、协作流程会不同，但UI框架可统一。建议设计一个 `TaskCard` 组件，通过 `type` 属性渲染不同交互。

3.  **寄语功能有温度但需审核**：随机推送和存储全站寄语，性能不是问题，但注意**内容审核**。初期可限定只有参与者及以上才能写入寄语，并且所有新寄语需标记为“待审核”，由Khub团队定期审核后进入公共库。

4.  **与后端提前对齐字段**：尤其是“任务所需角色”“临时组队邀请状态”“职级自动推荐规则”这些逻辑，早点约定API数据结构，避免后期返工。
