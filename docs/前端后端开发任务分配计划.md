## 团队配置

| 角色 | 定位 | 核心职责 |
|------|------|----------|
| FE-1（前端主力） | 架构 + 复杂交互 | 项目骨架、组件库、复杂详情页（多 Tab/状态流转） |
| FE-2（前端开发） | 页面量产 | 基于组件库快速产出 CRUD 列表页、管理页、简单页面 |
| BE-1（后端主力） | 架构 + 核心业务 | 项目骨架、鉴权体系、需求/任务核心状态机 |
| BE-2（后端开发） | 接口量产 | 数据建模、CRUD 接口、管理接口、通知 |

**分工逻辑**：FE-1 产出组件 → FE-2 消费组件产出页面；BE-1 搭架构 → BE-2 基于架构产出接口。

## 串行 vs 并行判断原则

```
串行（必须等前置完成）：
  ✗ 组件库未就绪 → 不能开始业务页面
  ✗ 后端骨架未完成 → 不能写业务接口
  ✗ 鉴权接口未完成 → 不能联调任何需要登录的页面
  ✗ DB Schema 未定 → 不能写对应 CRUD 接口

并行（互不阻塞，可同时进行）：
  ✓ 前端用 Mock 开发 ↔ 后端开发接口（各自独立）
  ✓ 同一 Sprint 内不同模块（需求模块 ↔ 任务模块，只要不共享组件）
  ✓ 同类型页面（5 个管理表格页模式相同，谁先谁后无所谓）
  ✓ 前端两人做不同页面（只要组件库已覆盖所需组件）

半并行（可以交错，但有软依赖）：
  ~ FE-1 产出 Dialog 组件 → FE-2 才能做审批弹窗页面
  ~ FE-1 产出 Tabs 组件 → FE-2 才能做详情页
  → 解法：FE-1 优先产出 FE-2 下一步需要的组件
```

### Sprint 0：基础设施 + 组件库（第 1-2 周）⚡️ 全串行

> 这是整个项目的地基，必须在业务开发前完成。4 人各自独立产出，但业务 Sprint 必须等 Sprint 0 合入 develop 后才能开始。

## 为什么这样分配

### FE-1 做复杂页面，FE-2 做量产页面

| 页面类型 | 数量 | 分配 | 理由 |
|----------|------|------|------|
| 复杂详情页（demand-detail, task-detail, team-detail） | 3 | FE-1 | 多 Tab、状态流转、嵌套组件，需要强架构能力 |
| CRUD 管理表格（demand/task/user/permission/system-log） | 5 | FE-2 | 模式统一，第一个做好后其余复制改字段 |
| 简单页面（login, register, forgot, onboarding, profile） | 5 | 分摊 | FE-1 做前 4 个（与鉴权关联），FE-2 做 profile |
| 列表页（my-demands, my-tasks） | 2 | FE-2 | 中等复杂度但模式相似 |
| 仪表盘（home, workbench） | 2 | 分摊 | FE-2 做 home（偏展示），FE-1 做 workbench（偏交互） |
| 消息中心 | 1 | FE-1 | 需要实时通知逻辑 |

### BE-1 做核心逻辑，BE-2 做标准 CRUD

| 模块 | 分配 | 理由 |
|------|------|------|
| 鉴权 + 中间件 | BE-1 | 全局基础设施，影响所有接口 |
| 需求/任务状态机 | BE-1 | 业务逻辑复杂，状态流转有分支 |
| 标准 CRUD（用户/文件/Profile） | BE-2 | 模式固定，快速产出 |
| DB 建模 | BE-2 | 需要整体思考表关系，一人统一设计更一致 |
| 通知系统 | BE-2 | 独立模块，事件驱动，与核心业务解耦 |

```
main              ← 生产发布，仅从 release 合入
├─ develop        ← 集成分支，所有 feature 合入此处
```

## 协作机制（远程团队适配）

> 团队全员远程开发，不依赖"集中联调"，改用契约驱动 + CI 自动验证 + 异步对齐。

### 核心原则：让机器替你联调

```
传统方式（需要凑时间）：
  FE 写完 → 等 BE 部署 → 约时间一起调 → 发现问题 → 修 → 再约

远程友好方式（异步闭环）：
  BE 写完接口 → 推代码触发 CI → 自动跑契约测试 → 通过即可用
  FE Mock 开发 → BE 接口就绪后 → FE 自行替换 Mock → 跑 E2E → 有问题提 Issue
```

### 接口契约驱动开发

```
1. BE 开发前：在 docs/API设计文档.md 补充完整接口定义
2. BE 同时输出：OpenAPI/Swagger JSON 文件（放在 backend/docs/openapi.json）
3. FE 基于 OpenAPI 自动生成 Mock（用 MSW + faker 或 openapi-mocker）
4. BE 接口完成后推代码 → CI 自动校验接口是否符合 OpenAPI 定义
5. FE 在自己的时间替换 Mock 为真实请求，跑本地测试验证
```

**好处**：不需要约时间，接口对不对机器说了算。

### 前后端集成验证（替代集中联调）

| 方式 | 怎么做 | 频率 |
|------|--------|------|
| **契约测试** | BE 推代码时 CI 自动对比 OpenAPI schema，不一致则阻塞合入 | 每次 PR |
| **Staging 环境** | develop 分支合入后自动部署到 staging（可用 Docker Compose + 云服务器或 Railway/Render） | 每次合入 develop |
| **FE 自验** | FE 开发完后指向 staging 环境跑一遍，有问题直接提 Issue + 截图 | 随时 |
| **异步 Bug Bash** | 每个 Sprint 末尾开一个 GitHub Issue "Sprint X 集成问题"，所有人 48h 内自行测试并回复 | 每 Sprint |

### 日常沟通（异步优先）

| 场景 | 工具 | 规则 |
|------|------|------|
| 日常同步 | 群消息（飞书/微信） | 每天发一条"今天做什么 / 卡在哪" |
| 接口讨论 | GitHub PR 评论 | BE 提交 API 文档变更 PR → FE 评论确认 → 合入 |
| 组件需求 | GitHub Issue | FE-2 提 Issue 描述需要什么组件 → FE-1 认领 |
| Bug 报告 | GitHub Issue + 截图/录屏 | 标明：环境(staging/local) + 复现步骤 + 期望行为 |
| 周会 | 视频（30 min） | 每周一次 Demo + 下周计划，非必须全员在线（可看录屏） |

### 组件库沟通

```
FE-2 需要新组件时：
1. 提 GitHub Issue：描述需求 + 贴 demo 截图 + 标明优先级
2. FE-1 评估：已有组件能否扩展 props？还是需要新建？
3. 新建：FE-1 在当前 Sprint 内补充，PR 完成后通知 FE-2
4. 扩展：FE-2 自己加 variant/prop 并提 PR 给 FE-1 Review
```

### Staging 环境建议

```yaml
# docker-compose.staging.yml（develop 分支自动部署）
services:
  backend:
    build: ./backend
    environment:
      - DATABASE_URL=postgresql://...
      - JWT_SECRET=staging-secret
    ports: ["8000:8000"]

  frontend:
    build: ./frontend
    environment:
      - VITE_API_BASE=http://staging-server:8000/api/v1
    ports: ["3000:3000"]

  db:
    image: postgres:16
    volumes: [pgdata:/var/lib/postgresql/data]
```

- 推荐平台：Railway / Render / 自有服务器 + GitHub Actions 自动部署
- develop 合入即部署，无需手动操作
- 所有人随时可访问 staging URL 验证功能
